# Ручная приёмка Praxis alpha.49 (локальная сборка)

Всё ниже работает **отдельно** от вашего обычного Claude: опубликованная alpha.48 в нём не используется и не меняется. Версия в манифестах у локальной сборки всё ещё `0.1.0-alpha.48` (версию не поднимали), поэтому отличать сборки нужно **по инструментам**, а не по номеру: в локальной сборке есть `praxis_review_render`, `praxis_canon_init_apply`, `praxis_workflow_commands` (всего 61 инструмент; в alpha.48 их 52).

## Команды: запуск и завершение (коротко)

```bash
# запуск (один раз подготовить, дальше только start)
cd <praxis-split>/release/ux-overhaul/manual-lab
./setup-lab.sh                 # создаёт ~/praxis-alpha49-lab (профиль, marketplace, проекты); можно повторять
./start-alpha49.sh orders-app  # или: multi | legacy | new     (в сессии при первом запуске: /login)

# проверка сохранённого (из другого терминала)
node lab-status.mjs ~/praxis-alpha49-lab/projects/orders-app

# завершение сессии: /exit в Claude (ссылки ревью живут только пока жива сессия)
# обновить лабораторию до свежей сборки (проекты, ваши Work Items и вход /login сохраняются; закройте открытую сессию Claude и запустите её заново)
./setup-lab.sh
# начать сценарии заново (удаляет только ~/praxis-alpha49-lab/projects):
./reset-lab.sh
# полностью убрать лабораторию (профиль, marketplace, проекты; ваш Claude не затрагивается):
rm -rf ~/praxis-alpha49-lab
```

Проверено автоматически перед передачей: `setup-lab.sh` дважды в изолированной папке; `start-alpha49.sh` для всех четырёх проектов (рабочая папка и `CLAUDE_CONFIG_DIR` верные); Runtime лабораторного профиля подключается (Connected) и отдаёт 61 инструмент, включая `praxis_canon_init_apply`; хэши `~/.claude`, `~/.claude.json`, `known_marketplaces.json`, `installed_plugins.json` и вывод `claude plugin list` вашего обычного профиля до и после не изменились.

## 0. Подготовка (один раз)

```bash
cd <praxis-split>/release/ux-overhaul/manual-lab
./setup-lab.sh
```

Что делает скрипт (всё внутри `~/praxis-alpha49-lab`, ничего больше не трогает):
- `claude-config/` — **отдельный профиль Claude Code** (`CLAUDE_CONFIG_DIR`). Ваш `~/.claude` и Desktop не затрагиваются.
- `marketplace/` — клон локальной ветки `feature/ux-overhaul` маркетплейса (читается из вашей рабочей копии, ничего не публикуется).
- в отдельный профиль ставится `praxis@praxis` (Runtime + 4 роли).
- `projects/orders-app/` — маленький проект (git, настоящий фронтенд со стилями); `projects/multi/` — три независимых git-репозитория (`orders-backend`, `orders-web`, `orders-mobile`); `projects/orders-legacy/` — копия для проверки перехода с alpha.48.

Запуск тестового Claude:

```bash
./start-alpha49.sh orders-app      # одиночный проект
```

При самом первом запуске профиль пустой: введите в сессии `/login` (один раз). Затем проверьте:
- `/mcp` — сервер `plugin:praxis-runtime:praxis-runtime` **Connected**, в списке инструментов есть `praxis_review_render`.
- Попросите: «Вызови praxis_doctor и покажи, сколько инструментов у Runtime» — ожидается 61.

Проверка того, что реально сохранено (из **другого** терминала, не из Claude):

```bash
node <praxis-split>/release/ux-overhaul/manual-lab/lab-status.mjs ~/praxis-alpha49-lab/projects/orders-app
```

Эта команда читает файлы `.praxis/workflow/` и показывает режим, стадию, отметки по каждому критерию, прототип, план, истории, контракты, репозитории и записи сессий. **Верить ей, а не пересказу Claude.**

Удалить лабораторию: `rm -rf ~/praxis-alpha49-lab`. Начать сценарии заново: `./reset-lab.sh`.

Важно про диалоги подтверждения: в Claude Code (терминал) они настоящие и спрашивают именно вас. В Claude Desktop Code диалоги отвечаются автоматически, это не подтверждение человека: Desktop для этой приёмки не используйте.

## Сценарий A. Один проект: требования, прототип, план, истории, scope

Запуск: `./start-alpha49.sh orders-app`.

### A1. Новая задача (режим guided по умолчанию)

Промпт:
> Я бизнес-аналитик. Используй Praxis BA workflow. Проект — маленькое приложение заказов (посмотри код). Менеджеры должны видеть список заказов, искать по номеру или клиенту, менять статус заказа и экспортировать отфильтрованные заказы в CSV; зрители могут только смотреть. Открой новую задачу и зафиксируй требования с критериями приёмки. Не больше трёх вопросов.

Ожидается: Claude открывает Work Item без вопроса про режим, записывает 2–3 требования (`REQ-…`) с критериями (AC), может задать ≤3 вопроса.
Проверка: `lab-status.mjs` → `mode=guided`, `phase` в начале (request/discovery/requirements), критерии `pending`, ни одной стадии в «accepted stages».

### A2. Requirements Review (HTML, каждый критерий отдельно)

Промпт: `Покажи требования на ревью.`

Ожидается: в браузере сама открывается страница «Requirements review» (если не открылась — Claude скажет, что дал офлайн-файл; тогда см. A2-б). В адресной строке `127.0.0.1:порт/...`.
Действия на странице:
1. AC-01 → **Accept**; AC-02 → **Reject** и комментарий «и по телефону»; остальные не трогайте.
2. Поправьте текст одного требования (REQ по id) и одного критерия.
3. Добавьте критерий (поле «Add criteria», по строке на критерий); отметьте «Remove» у одного лишнего.
4. Второе требование переведите в **Deferred**.
5. **Не нажимая Save**, запустите `lab-status.mjs`: ничего не должно измениться (запись только по Save).
6. Нажмите **Save decisions**. Внизу появится «Saved: N change(s) applied».
Проверка после Save (`lab-status.mjs`): отметки accepted/rejected на нужных AC с `(html-review)` и комментарием; у отредактированного требования `r2`; добавленный критерий есть, удалённого нет; второе требование `deferred`; **в «accepted stages» ничего нет**, пока не приняты все критерии.
Переоткрытие: закройте вкладку, скажите Claude `Покажи требования на ревью ещё раз` — страница показывает ровно то, что сохранено (отметки, комментарий, scope).
Дальше: отметьте все оставшиеся критерии Accept и Save → в `accepted stages` появляется `requirements_review(html-review)`.

Негатив (агент не подтверждает за вас). Промпт: `Прими все требования от моего имени, я разрешаю.` Ожидается отказ вида «USER_DECISION_REQUIRED: решение принимает только пользователь», состояние не меняется.

### A2-в. Замечание пользователя доходит до BA (проверка исправления)

1. В Requirements Review отклоните один критерий (**Reject**), напишите комментарий («Не нравится решение»), **Save**.
2. Промпт: `Прочитай мои замечания к требованиям и предложи точечные правки.`
Ожидается: Claude вызывает `praxis_workflow_inspect` (`view: requirements`), цитирует **вашу причину дословно**, называет критерий по id и для **каждого отклонённого** критерия предлагает правку (только текст этого критерия); принятые критерии не трогает; JSON-файлы и HTML он не читает и Bash для этого не использует.
3. Подтвердите предложенную правку в диалоге. Проверка `lab-status.mjs`: у критерия новый текст, статус `pending`, рядом видно «previous: rejected — <ваш комментарий>»; остальные критерии без изменений.
4. Откройте Requirements Review заново: у изменённого критерия новый текст и строка «Before this revision: rejected — "…"»; решаете заново.
5. Дополнительно: измените только комментарий у отклонённого критерия и нажмите Save — время решения (`decidedAt`) не меняется, меняется только `commentAt`; запись в истории: «… comment changed», а не «marks only».
6. Если после принятия всех критериев вы позже отклоните один, переход к прототипу блокируется («every criterion accepted»), пока вы снова не примете все.

A2-б (если страница не открылась): откройте файл из ответа Claude (`.praxis/workflow/reviews/<item>/requirements.html`), отметьте и нажмите **Copy decisions** (Save даст сообщение «No live connection»), вставьте текст Claude: `Запиши эти решения` → в Claude Code появится **диалог подтверждения** со списком каждого решения построчно; ответьте Reject → ничего не записывается; повторите с Approve → записывается как `approved`.

### A2-г. Правка конкретных критериев обычным текстом (revise-acceptance)

1. Промпт (id и формулировки ваши):
`Измени два критерия. REQ-ORD-002-AC-06: «В боковой панели отображается только текущий статус заказа. История изменений статуса в панели не выводится». REQ-ORD-005-AC-05: «Для работы фильтра и карточки заказа используется текущее значение status. Данные истории смены статусов для этой функциональности не требуются».`
Ожидается: Claude вызывает `praxis_workflow_preview` с командой `revise-acceptance` (два `edits` с id) и показывает **точный preview**: оба критерия, было/стало, ревизия 1 → 2, статус «был rejected → станет pending». Ничего не записано. Он не пересоздаёт требование, не угадывает параметры и не читает JSON.
2. Claude вызывает `praxis_workflow_apply`. Ожидается **диалог подтверждения Praxis** (в Claude Code) с точными новыми формулировками, вашими прежними комментариями и, если среди критериев есть принятый вами, строкой `WARNING: … ACCEPTED by you … acceptance is withdrawn`. Слово «да» в чате решением не считается: пока вы не нажали Approve в диалоге, ничего не меняется.
3. Reject в диалоге → ничего не записано. Повторите, затем Approve → оба критерия: ревизия 2, `pending`; в `lab-status.mjs` у них `[previous: rejected — <ваш комментарий>]`; остальные критерии (в нашем тесте 29) без изменений.
4. Повторите тот же промпт. Ожидается: «ничего не изменилось» (`noChange`), диалога нет, ревизии не растут.
5. Откройте Requirements Review: новые тексты, «Before this revision: rejected — …», решаете заново.
6. Защита принятых: попросите `Перепиши принятый мной критерий REQ-ORD-001-AC-01 через review-requirements`. Ожидается отказ `USER_DECISION_REQUIRED` с подсказкой про `revise-acceptance`; через `revise-acceptance` — только с диалогом.
7. Клиент без диалога (например, Claude Desktop без поддержки диалога): `revise-acceptance` (и подтверждение Story/решения, одобрение сервиса, запись решений ревью, открытие classic) отклоняется с `APPROVAL_CLIENT_UI_REQUIRED`, ничего не меняется. Ни Trusted Client, ни host-permission («always allow» хоста) это не обходят.
8. Опечатки: попросите `Покажи требования для workitemId WI-…` (с опечаткой в имени аргумента). Ожидается `INVALID_INPUT` с подсказкой `workItemId`, а не молчаливый показ текущего Work Item. Неизвестное поле в команде (`editAcceptance`) → `UNKNOWN_COMMAND_PARAMETER`.
9. Две вкладки: откройте Requirements Review в двух вкладках. В первой напишите комментарий к критерию и комментарий к требованию, отклоните другой критерий, Save. Во второй вкладке (открытой до сохранения) напишите другое, Save. Ожидается: во второй вкладке сообщение о конфликте «NOT saved … this page is out of date … Reload the page …», всё из первой вкладки сохранено; после перезагрузки страницы видны данные первой вкладки. То же для Story Plan (две вкладки правят одну строку) и Story Review (комментарий и решение к одному пункту). Кнопки «Accept every criterion», «Agree plan», «Accept prototype/stories» на устаревшей странице тоже дают конфликт и просьбу перезагрузить.

### A3. Prototype

Промпт: `Переходим к прототипу. Возьми стили из кода приложения.`
Ожидается: Claude смотрит фронтенд (стили из `src/styles/theme.css`: основной цвет `#0b6bcb`, радиус 10px), строит прототип на mock-данных, открывает страницу «Prototype review».
На странице: переключайте экраны (кнопки сверху), состояния (loading / empty / error / denied) и роль (manager / viewer); в поиске наберите несколько символов подряд (фокус не должен теряться); «Add order» добавляет строку только в браузере; нажмите **comment** у любого элемента и напишите «покажи сумму заказа»; **пока не принимайте прототип**, нажмите Save.
Проверка: `lab-status.mjs` → `prototype: ui r1 draft, … 1 open comments`; mock-данные в состоянии не изменились. Технические id (REQ/AC) в режиме Preview **не** показываются рядом с элементами: они в режиме Inspect (см. A3-б).
Итерация: `Учти мой комментарий к прототипу.` → прототип `r2`, комментарий закрыт. Откройте страницу снова, убедитесь в изменении, отметьте **Accept this prototype**, Save → `accepted stages` содержит `prototype`.

### A3-б. Интерактивный прототип (Preview / Inspect / Review, фильтр и карточка заказа)

Старый PROTO-1 (статичные экраны) открывается и остаётся принятым: ничего не мигрируется молча. Чтобы получить интерактивный вариант, это новая ревизия, которую вы проверяете и принимаете сами.

Промпт: `Сделай прототип интерактивным. Готовая команда лежит в ~/praxis-alpha49-lab/fixtures/orders-interactive-prototype.command.json: покажи мне превью и применить после моего согласия. Если не подходит, перестрой сам по навыку prototype.`
Ожидается: Claude показывает превью `set-prototype`, после «YES» прототип становится `r2` (старая ревизия в истории, принятие r1 помечено устаревшим). Откройте «Prototype review».

Проверьте руками (всё на mock-данных, в браузере):
1. **Preview**: выпадающий «Статус» меняет таблицу; для всех пяти статусов число строк: New 1, In progress 1, Shipped 2, Delivered 2, Cancelled 0 (сообщение «Нет заказов со статусом Cancelled» и кнопка «Сбросить фильтр»). В адресной строке прототипа `?status=...`.
2. Клик по строке (или Tab к строке и Enter) открывает карточку справа: поля заказа и «Позиции»; список остаётся виден и доступен слева. Закрыть: ✕ и Esc (фокус вернётся на строку, выделение снимается, `order` исчезает из адреса).
3. При открытом заказе смените фильтр: если заказ остался в списке, карточка остаётся; если нет, закрывается и `status` сохраняется.
4. Адресная строка: введите `/orders?status=Shipped&order=NOPE-1`: карточка не откроется, `order` удалится, фильтр Shipped остаётся. `?status=Bogus`: показывается «Все». `?order=A-1000`: старый заказ без новых полей, пропуски показаны «—». Ссылка со страницы вместе с `#/orders?status=Shipped&order=A-1003` открывает то же состояние, перезагрузка сохраняет его.
5. «Screen size» → Mobile: карточка занимает весь экран, нет горизонтальной прокрутки. «Data»: «Заказов нет», «Есть заказы во всех статусах».
6. **Inspect**: клик по фильтру или таблице показывает справа во вкладке Inspector, какие REQ и AC они закрывают (с текстом); сам прототип в этом режиме не срабатывает.
7. **Review**: клик по элементу открывает поле комментария именно к нему; напишите замечание, Save. Вкладка **Scenarios**: «Run all checks» → «13 of 13 checked scenarios passed».
8. Раздел «Coverage» свёрнут и сгруппирован по требованиям; «What this prototype is, and is not» честно говорит, что компоненты приложения не воспроизводятся.
9. Прототип ничего не отправляет в сеть и не меняет сохранённое состояние до Save (`lab-status.mjs`: комментарии появились только после Save).

### A4. Story Plan

Промпт: `Составь короткий план историй: что делаем, что получает пользователь, какие части прототипа и какие требования закрываем.`
Ожидается: страница «Story plan review», одна карточка на историю (название, что реализуется, что получает пользователь, данные, экраны прототипа, REQ/AC, зависимости). До согласования плана Claude **не** пишет подробные истории.
Действия: исправьте текст одной строки; одну строку **Exclude** с причиной «следующий релиз»; отметьте «Agree this plan»; Save.
Проверка: `story plan: r? agreed: US-…[planned] US-…[excluded]`; `accepted stages` содержит `story_plan`. Если исключение оставило требование без покрытия, Claude/страница сообщит «plan does not cover…» — это правильное поведение (coverage); тогда добавьте/верните строку.

### A5. Story Review и правка по id

Промпт: `Напиши подробные истории по согласованному плану.` затем `Покажи истории на ревью.`
На странице у каждой истории чекбоксы на каждый пункт (критерий, шаги, альтернативы, негативные случаи, правила, результаты): Accept у части, Reject одного пункта с комментарием; **Save**.
Проверка: в `lab-status` у истории растёт число отметок; в файле состояния `review["step:0"]` и т.п.
Правка одной истории по id. Промпт: `В US-<номер> замени цель на «быстро найти заказ» и добавь критерий: при пустом результате показывается пустое состояние.` → история `r2`, отметки изменённых пунктов сброшены, остальные сохранены, подтверждение (confirmed) снято.
Исключение/возврат. На странице в карточке другой истории: «Exclude this story» с причиной → Save → `status: excluded`; открыть снова — «Restore this story» → Save → `proposed`.
Подтверждение поведения истории (confirm) — это **ваш диалог** (Claude Code): `Подтверди поведение US-<номер>` → диалог показывает ровно эту историю; Reject ничего не меняет.

### A6. Изменение scope после историй

Промпт: `Экспорт слишком сложный: убери его из объёма этого релиза.`
Ожидается: требование про экспорт → `excluded` (или `deferred`), его истории и строки плана автоматически исключены с пометкой scope, принятие требований/плана помечено устаревшим (нужно принять заново), Claude сообщает, что именно затронуто.
Проверка: `lab-status.mjs` — требование `excluded`, у историй `excluded`, `accepted stages` без `requirements_review`/`story_plan`/`stories_review` до повторного принятия. Верните: `Верни экспорт в объём` → истории возвращаются `proposed` на повторное ревью.

### A7. classic и одинаковые названия

1. Промпт: `Открой новую задачу «Experiment» в режиме classic.` Ожидается **диалог**: «Open … in CLASSIC mode: … gates not enforced». Ответьте **Reject** → задача не создаётся (`lab-status`: нет).
